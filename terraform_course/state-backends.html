State, backends, and locking

State maps your config to real objects. A shared backend keeps one copy. Locking stops two applies from writing that copy at once. The lock mechanism depends on the backend and the version.

Sign in to save your place.

Picture it this way

State is the notebook that says which locker number belongs to which name on the list. If two people write in the notebook at once, the numbers get crossed. A lock is the pencil you have to be holding to write.

Local state is a starting point

By default the state file is terraform.tfstate in the working directory. That is fine for a solo lab. It is a bad place for a team. The file contains ids and any secret attributes the provider stored. Do not commit it.

Never edit the state file by hand to fix a typo. Use the commands and blocks in the lifecycle lesson. A hand edit is how the next plan destroys something real.

S3 locking changed

The S3 backend can store state in a bucket. Older Terraform releases locked that state with a DynamoDB table. Terraform 1.10 added an S3 lock file through use_lockfile. Current HashiCorp S3 backend docs describe DynamoDB locking as deprecated and scheduled for removal, and describe use_lockfile as the lock switch.

Those sentences are about HashiCorp Terraform's documented backend. An older binary does not grow use_lockfile because a doc page mentions it. OpenTofu has its own S3 locking work. Do not delete a DynamoDB lock table until every runner that touches that state is on a version that locks the way you think.

After a backend change, terraform init -reconfigure is the usual next command. Read the upgrade guide for the version you are moving to before you drop the old lock.

Situation What to do
One person, a lab, terraform_data Local state is enough
A team on current Terraform S3 docs Turn on use_lockfile and grant access to the .tflock object
Runners still on an older Terraform Keep the lock mechanism those runners understand
OpenTofu in the same bucket Read OpenTofu's backend page, not only HashiCorp's

From the previous lab directory, list the state file after a plan or apply. Add it to a local ignore file if you use git.

terraform plan
ls -la terraform.tfstate 2>/dev/null || echo "no state yet — plan may be enough"
printf '%s\n' '.terraform/' '*.tfstate' '*.tfstate.*' >> .gitignore

Concept summary

  • State is the map from blocks to real objects. Do not commit it.
  • S3 locking with use_lockfile and DynamoDB locking are not the same mechanism.
  • Check the backend page for the binary version that will run apply.
