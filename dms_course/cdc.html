CDC and log positions

Change data capture reads the source database's change log from a saved position. The log name is different on every engine. If the log is gone, DMS cannot invent the missing changes.

Sign in to save your place.

Picture it this way

CDC is reading the shop's diary instead of recounting every item. If someone throws the diary away, you cannot reconstruct Tuesday afternoon.

A position, not a feeling

The task stores a position in the source log. After a restart it tries to continue from that position. Full load plus CDC starts the log reader before or as the load runs, so changes during the load are not dropped on the floor. The exact handshake is in the engine's DMS page. Do not skip that page for the engine you use.

If the position is older than the logs the source still has, CDC cannot resume. Retention is a source-database setting: binary log days on MySQL, a replication slot that stops PostgreSQL from recycling WAL, archive logs on Oracle, and the SQL Server retention for CDC. A slot or a log that fills the disk is the other failure. Watch it.

The log is not the same object

MySQL and MariaDB: the binary log, usually row format, a file and position or a GTID, and enough retention. PostgreSQL: wal_level = logical, a replication slot, and an LSN. The PostgreSQL course's replication lesson is the database side of slots. Oracle: supplemental logging and an SCN. SQL Server: the CDC or replication feature the DMS source page requires for that edition, and an LSN.

Turning those settings on can require a restart or extra disk. Do it in a change window, not as a surprise during the load.

PostgreSQL LSN and a slot WAL for that slot

Concept summary

  • CDC resumes from a stored log position.
  • MySQL, PostgreSQL, Oracle, and SQL Server do not share one setting name.
  • If the log is gone, the task cannot catch up. You reload.
