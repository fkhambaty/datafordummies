Schema conversion paths

Same engine family can often keep its schema. A different engine needs a conversion step before DMS is asked to load rows into tables that make sense.

Sign in to save your place.

Picture it this way

Moving shelves between two shops of the same chain is mostly carrying boxes. Moving into a shop that uses different shelf labels means reprinting the labels first. The boxes come after.

Homogeneous path

PostgreSQL to PostgreSQL, or PostgreSQL to Aurora PostgreSQL, is homogeneous. Tables, types, and many constraints already match. You still check extensions, large objects, sequences, and users. Native logical replication or dump and restore can be a better tool than DMS. DMS is one option, not a rule.

The PostgreSQL replication lesson covers slots if you choose the database's own replication instead of DMS.

Heterogeneous path

Oracle or SQL Server to Aurora PostgreSQL is heterogeneous. Run a conversion assessment with DMS Schema Conversion or with AWS SCT, fix the action items a person must touch, and apply the schema before the full load. DMS can create tables, and those tables will not include a correct translation of procedural code.

Generative AI conversion, where AWS offers it for a pair, still needs a person to read the result. The user guide marks which pairs have it. Do not assume every source and target pair does.

A virtual target in DMS Schema Conversion lets you assess before the real database exists. You still need a real target before you apply the code and start the data task.

Concept summary

  • Homogeneous moves still need a check. They do not always need DMS.
  • Heterogeneous moves convert schema before the row copy.
  • Generated code and generated AI output are drafts.
