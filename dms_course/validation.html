Validation and CloudWatch

Validation compares rows. CloudWatch shows whether the task is keeping up. Neither one proves the application is ready.

Sign in to save your place.

Picture it this way

Validation is counting the boxes on both docks. CloudWatch is the clock on the truck. A matching count does not mean the shop signs were translated.

Data validation

Turn validation on for a task when you need DMS to compare source and target rows. It adds load. It does not replace a query you wrote for a table you care about. Mismatches show up as a validation state, not as a green full-load percentage.

Validation will not notice a wrong procedure, a missing index you meant to add later, or an application still pointed at the source.

Metrics worth naming

CloudWatch metrics include full-load throughput and CDC latency on the source and the target. The useful question is whether latency is growing. A task that is "running" with climbing CDC latency is falling behind.

Task logs go to a CloudWatch log group. When a table fails, the log line is more useful than the task's overall percentage. A replication instance that is out of memory or storage fails in those logs and in instance metrics. Serverless tasks have capacity metrics instead of an instance class graph. Concept summary

  • Validation compares rows. It does not test procedures or the application.
  • Watch CDC latency, not only the running badge.
  • Logs explain a failed table. The percentage does not.
