Picture it this way

Production is the lock, the spare key, and the window. The lock is encryption, network, and who may see which rows. The spare key is a snapshot you have restored once. The window is the history of queries, so you hear trouble before a user does.

Security you can explain

Encrypt the warehouse. Keep it in a private subnet unless you have a reason you can write down. Use IAM roles for COPY and Spectrum. Use security groups that name the clients. Turn on audit logging to S3 or CloudWatch when the data is sensitive enough that you will be asked who ran a query.

Row-level security and dynamic data masking are how you keep one table and still hide rows or columns from a group. They are not a substitute for a separate account when two companies must not share a failure domain. Test with a user who must see nothing. An admin query is not that test.

Snapshots, patches, and signals

Automated snapshots are the spare key for provisioned clusters. Know the retention and whether a cross-region copy exists. Serverless recovery uses the namespace's recovery points. Either way, restore once into a scratch warehouse and run a count. A snapshot you have never opened is a rumor.

Maintenance windows patch the engine. Read the current maintenance notes before you schedule a load through that window. For signals, keep a short dashboard on SYS_QUERY_HISTORY: failed queries, queue time, and the longest scans. CloudWatch covers cluster health such as CPU and disk on the shapes that publish those metrics. Alert on queue time and failed loads, not only on CPU.

SELECT COUNT(*) AS failed_queries
FROM sys_query_history
WHERE status = 'failed'
  AND start_time > DATEADD(hour, -24, GETDATE());

Data sharing is not a backup

A consumer can see current tables. It does not give you yesterday after someone deletes the producer. Snapshots do that.
